# Obsidian ↔ SQLite Bridge — Phase 2 Architecture

**Document purpose:** Architecture proposal for Reed to implement the two-way sync between the Obsidian vault at `/Volumes/GIT/CLAUDE/SHARED_WORK_FOLDER/` and the workspace database at `db/workspace.db`.

---

## 1. Tables in Scope

| Table | Sync Direction | Notes |
|---|---|---|
| `journal_entries` | **Both ways** | Boss writes in vault daily notes; DB is the structured replica. |
| `tasks` | **DB → vault only** (read-only in vault) | Tasks are created/updated via the web app or SQL; vault shows them as a live view. Vault is not a task editor. |
| `activity_log` | **DB → vault only** (read-only in vault) | Append-only log; no business writing back from vault. |
| `team_members` | Optional / DB → vault | A generated roster note could be useful; low priority. |

---

## 2. Vault → DB: Daily Notes Sync

### Recommended approach: **File-watcher script (`sync_journal.py`)**

**Why not a pre-commit hook?** A pre-commit hook fires on every `git commit`, not on every save. Thomas edits notes continuously throughout the day; waiting until commit creates an unbounded lag and ties journaling to git discipline. A pre-commit hook also runs synchronously in the commit path — any slow Python import would noticeably delay `git commit`.

**Why not `make sync`?** A manual `make sync` requires Thomas to remember to run it. The value of the bridge is ambient — notes appear in the DB without friction.

**Recommended: a lightweight watcher using `watchdog` (Python library)**

```
scripts/sync_journal.py        # the watcher
scripts/requirements.txt       # watchdog, frontmatter, python-dateutil
```

**Behavior:**
1. Watch `journal/` for `*.md` file close-write events.
2. On event: parse frontmatter (date) + body from the changed file.
3. Upsert into `journal_entries`:
   ```sql
   INSERT INTO journal_entries (date, title, content)
   VALUES (?, ?, ?)
   ON CONFLICT(date) DO UPDATE SET
     content = excluded.content,
     updated_at = strftime('%Y-%m-%dT%H:%M:%SZ','now');
   ```
4. Log the upsert to `activity_log` with actor=`obsidian-bridge`.

**Running the watcher:** Reed should create a launchd plist at `~/Library/LaunchAgents/com.sharedworkfolder.journal-watcher.plist` so it starts on login and restarts on crash. The plist is lightweight (one Python process, nearly zero CPU when idle).

**Parsing the daily note body:** The sync script should extract only the **"Journal entry (syncs to DB)"** section (the last H2 block in the daily template) as the canonical prose to store in `journal_entries.content`. The "Today's tasks" and "Activity log" sections are DB-derived and should be stripped before writing to avoid a circular-import loop.

## 3. DB → Vault: Generated Dashboard Notes

### Recommended approach: **Python-generated read-only notes, regenerated by the watcher on DB change**

Three options were evaluated:

| Option | Verdict |
|---|---|
| **Dataview-via-SQL plugin** (e.g. `obsidian-db-folder` or `dataview` with custom JS) | Dataview queries vault frontmatter, not external SQLite. Bridging it to SQLite requires an intermediate plugin (e.g. `obsidian-sqlite`) that is poorly maintained and adds a runtime dependency inside Obsidian. Not recommended. |
| **Inline Templater queries against a SQLite bridge script** | Templater can call shell commands, which could invoke a Python script returning query results. This works but makes the vault non-portable (relies on external Python + DB path baked into templates). Also fails when Obsidian is open on a machine without the bridge. |
| **Python-generated read-only notes** | Cleanest separation. The bridge regenerates fixed-path Markdown files (`journal/_dashboard/tasks-today.md`, `journal/_dashboard/recent-activity.md`) whenever the DB changes. Obsidian just reads them — no plugin dependency, portable Markdown on disk. |

**Recommended: Python-generated read-only notes**

```
journal/_dashboard/tasks-today.md        # regenerated on DB write
journal/_dashboard/recent-activity.md   # regenerated on DB write
journal/_dashboard/task-index.md        # full task list, regenerated daily
```

The watcher already listens to DB changes (SQLite WAL mode supports `inotify`/`kqueue` on the `-wal` file). On any DB change, regenerate the dashboard notes as Markdown tables. Thomas opens them in Obsidian and sees live data — read-only, clearly marked with a regeneration timestamp at the top.

Add `^journal/_dashboard/` to `.obsidian/app.json` `userIgnoreFilters`? **No** — leave them visible. They are knowledge-surface files Thomas will want to see. Just mark them `read-only: true` in frontmatter as a convention (Reed can enforce this in the watcher by not allowing the sync-back to write these paths).

## 4. Conflict Resolution

### Default rule

**Vault is source of truth for prose; DB is source of truth for structured records.**

| Data type | Source of truth | Replica |
|---|---|---|
| Daily note prose (journal body) | `journal/YYYY-MM-DD.md` | `journal_entries.content` |
| Task status, assigned_to, dates | `tasks` table | None (vault shows read-only) |
| Activity log entries | `activity_log` table | None (vault shows read-only) |

### What "conflict" looks like

A true conflict occurs when both the vault file AND the DB row were modified between watcher runs (e.g., watcher was down, Thomas edited the note, and also a script updated `journal_entries.content` directly). Resolution:

1. **Timestamp wins:** compare `journal_entries.updated_at` vs file modification time. Newer timestamp wins.
2. **Escape hatch:** if both were modified within 60 seconds of each other (ambiguous), write both versions to `journal/_conflicts/YYYY-MM-DD-conflict.md` and alert Thomas via a placeholder line in the dashboard note: `> ⚠️ Conflict detected for YYYY-MM-DD — see journal/_conflicts/`.
3. **The bridge never silently discards data.** Append, don't overwrite, when in doubt.

## 6. Risks and Open Questions

### Risks

1. **SQLite WAL locking:** The bridge script must use `isolation_level=None` (autocommit) or short transactions to avoid blocking the web app's writes. Test with concurrent Flask + bridge writes under load.
2. **Large daily notes:** If Thomas writes multi-KB prose, the upsert to `journal_entries.content` is fine — SQLite TEXT is unlimited. But Dataview-style queries over large content fields slow down. Keep the dashboard queries narrow (don't `SELECT content`).
3. **Obsidian rename vs. watcher:** If Thomas renames a journal file (unlikely with date-prefixed names, but possible), the watcher must handle the `moved` event and update the DB date field — or create a new row. Current schema has `date` as UNIQUE, so a rename from 2026-05-06 to 2026-05-07 would need a `DELETE + INSERT`. Reed should handle this explicitly.
4. **Plugin trust on first open:** Community plugins downloaded manually (Templater, Dataview, Obsidian Git) will show an "untrusted plugin" warning on first vault open. Thomas must manually click "Trust" in the Obsidian UI for each. This is by design — Obsidian's security model. Not a blocker, just a UX step.

### Open Questions (flag for Thomas)

1. **Should the watcher run always-on (launchd) or on-demand (`make sync`)?** Cairn recommends always-on, but if Thomas wants to stay offline-first and sync explicitly, `make sync` is viable.
2. **Dashboard notes folder — should `journal/_dashboard/` be in `.gitignore`?** They are generated/ephemeral. Probably yes, unless Thomas wants them versioned for historical snapshots.
3. **`activity_log` retention in vault:** The log grows unboundedly. Should the generated `recent-activity.md` show last 20 rows, or last 7 days, or paginated by month? Need a preference.
4. **Obsidian Git plugin scope:** Should Obsidian Git auto-commit the whole vault (including `team/`, `journal/`, `owner_inbox/`) on a schedule, or only commit on manual trigger? Auto-commit on timer is noisy if Thomas is mid-thought. Recommend: commit on Obsidian quit + daily scheduled commit at midnight.
